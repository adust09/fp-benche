# Rust: Imperative vs Functional Style Performance Comparison

Rustの命令型スタイル（forループ、mut変数、インデックス追跡）と関数型スタイル（イテレータチェーン、fold、from_fn）の性能差を測定した結果をまとめる。

**測定環境**: Linux 6.18.12+kali-amd64 / Rust edition 2021 / `--release` (LTO, codegen-units=1, opt-level=3)
**測定ツール**: Criterion 0.5（`--quick`モード）
**測定日**: 2026-03-12

> **注意**: ベンチマークはシステム負荷やCPUキャッシュ状態により実行毎に数値が変動する。
> 以下は代表的な1回の結果であり、傾向の把握を目的とする。

---

## 1. マージソート — インデックスベース vs イテレータベース

**比較対象**: `merge`関数のみ（再帰分割構造は同一）

| 手法 | `while` + `i, j` インデックス | `Peekable` + `from_fn` + パターンマッチ |
|------|------|------|

| サイズ | imperative (中央値) | FP (中央値) | 差分 |
|--------|-------------------|------------|------|
| 1,000 | 51.2 µs | 71.9 µs | **+40%** |
| 10,000 | 565 µs | 809 µs | **+43%** |
| 100,000 | 7.02 ms | 10.21 ms | **+45%** |

### 分析

FP版が一貫して **~40-45% 遅い**。`Peekable`イテレータの`peek()`は内部で`Option`にキャッシュするため、各比較で二重間接参照が発生する。命令型の`left[i]`は単純なインデックスアクセスであり、CPUのプリフェッチやベクトル化の恩恵を受けやすい。

`iter::from_fn`のクロージャも、ループ本体と比べてインライン化の機会が制限される可能性がある。サイズに関わらず差分が安定している（~40-45%）ことから、定数倍のオーバーヘッドであると推測される。

```
imperative: while i < left.len() && j < right.len() { left[i] vs right[j] ... }
FP:         from_fn(|| match (li.peek(), ri.peek()) { ... })
```

## 2. エラトステネスの篩 — whileループ vs fold/for_each

**比較対象**: 同一アルゴリズム O(n log log n)、同一データ表現 `Vec<u8>`

| サイズ | imperative (中央値) | FP (中央値) | 差分 |
|--------|-------------------|------------|------|
| 100,000 | 154 µs | 427 µs | **+177%** |
| 1,000,000 | 1.95 ms | 3.76 ms | **+93%** |
| 10,000,000 | 36.2 ms | 44.2 ms | **+22%** |

### 分析

小サイズで **最大2.8倍** の差があるが、サイズが大きくなるにつれて差は縮小（10Mで+22%）。

```rust
// FP版: foldが各素数pごとにVecの所有権を移動→返却する
(2..=limit).fold(vec![1u8; n + 1], |mut sieve, p| {
    if sieve[p] == 1 {
        (p * p..=n).step_by(p).for_each(|m| sieve[m] = 0);
    }
    sieve  // ← 所有権の移動（ムーブ）
});
```

`fold`はイテレーション毎にアキュムレータ（`Vec`）をムーブで渡す。Rustのムーブはコピーではない（ポインタの移動のみ）が、`fold`のクロージャ境界がコンパイラのループ最適化（ベクトル化、ループアンロール）を阻害する可能性がある。

サイズが大きくなると篩のマーキング（`for_each`内のメモリ書き込み）がボトルネックとなり、ループ制御のオーバーヘッドが相対的に小さくなるため差が縮小する。

> **補足**: 真に不変（ミューテーション無し）の篩は試行除算 O(n√n) が必要であり、これはスタイル変更ではなくアルゴリズム変更となる。

## 3. ワードカウント — ネストforループ vs flat_map + fold

**比較対象**: 同一ロジック（split_whitespace → trim → lowercase → HashMap集計）、I/O無しのインメモリ版

| サイズ | imperative (中央値) | FP (中央値) | 差分 |
|--------|-------------------|------------|------|
| 1,000行 | 811 µs | 824 µs | **+2%** |
| 5,000行 | 3.39 ms | 3.69 ms | **+9%** |
| 10,000行 | 7.10 ms | 7.13 ms | **+0.4%** |

### 分析

ほぼ **同等の性能**（差分は2-9%のノイズ範囲内）。

```rust
// FP版: flat_map + fold — 中間コレクションを生成しない
lines.iter()
    .flat_map(|line| line.split_whitespace().map(...).filter(...))
    .fold(HashMap::new(), |mut acc, word| { *acc.entry(word).or_insert(0) += 1; acc })
```

ワードカウントではボトルネックが**文字列処理とHashMapの操作**にあり、ループ制御構造の差は無視できるレベル。`flat_map`は中間`Vec`を生成せず遅延評価されるため、ネストforループと同等のメモリアクセスパターンになる。

**これが「ゼロコスト抽象化」が最もよく機能するパターン** — イテレータチェーンが実質的にforループと同一コードにコンパイルされる場合。

## 4. グループ集計 — forループ vs fold アキュムレータ

**比較対象**: `HashMap<&str, (f64, u64)>` への集約（5カテゴリ）

| サイズ | imperative (中央値) | FP (中央値) | 差分 |
|--------|-------------------|------------|------|
| 10,000 | 185 µs | 235 µs | **+27%** |
| 100,000 | 1.85 ms | 2.12 ms | **+14%** |
| 1,000,000 | 19.4 ms | 19.4 ms | **~0%** |

### 分析

小サイズで差が出るが、1M件では **完全に同等**。

小サイズでのオーバーヘッドは`fold`のクロージャ呼び出しコストと推測される。大サイズでは`HashMap`のバケット操作（ハッシュ計算、衝突解決、メモリアロケーション）が支配的となり、ループ制御の差が埋もれる。

篩と同様にサイズ増加に伴い差が縮小するパターンだが、ワードカウントよりは差が大きい。これはワードカウントが文字列処理（`to_lowercase`等）という重い操作を含むのに対し、グループ集計の各イテレーションが軽量（`f64`の加算と`u64`のインクリメント）であるため、ループ制御のオーバーヘッドが相対的に目立つためと考えられる。

## 5. チャネルスループット — forループ vs for_each/fold（帰無仮説）

**比較対象**: crossbeam bounded(1024) チャネルでの送受信

| メッセージ数 | imperative (中央値) | FP (中央値) | 差分 |
|------------|-------------------|------------|------|
| 10,000 | 473 µs | 511 µs | **+8%** |
| 100,000 | 3.82 ms | 2.83 ms | **-26%** |

### 分析

**帰無仮説は支持される** — チャネル同期がボトルネックであり、ループスタイルの差は測定ノイズに埋もれる。10Kでは+8%、100Kでは-26%と方向すら安定しないことが、スタイルの差ではなく**スレッドスケジューリングのジッタ**であることを示している。

```rust
// FP版: sender側
(0..n).for_each(|i| tx.send(i).expect("send failed"));
// FP版: receiver側
rx.iter().fold(0u64, |acc, val| acc.wrapping_add(val))
```

チャネルの`send()`/`recv()`は各呼び出しでアトミック操作やスレッド間同期を行うため、1イテレーションあたりのコストがループ制御の数ナノ秒をはるかに上回る。

## 総合まとめ

| ベンチマーク | 予測 | 実測 | ゼロコスト? |
|------------|------|------|-----------|
| マージソート（merge関数） | ~0% | **+40-45%** | No |
| エラトステネスの篩 | ~0% | **+22-177%** (サイズ依存) | No |
| ワードカウント | ~0% | **+0.4-9%** | **Yes** |
| グループ集計 | ~0% | **0-27%** (サイズ依存) | ほぼYes (大サイズで) |
| チャネル | ~0% | **ノイズ範囲** | Yes (同期が支配的) |

### ゼロコスト抽象化が成立する条件

1. **イテレーション本体が十分に重い場合** — 文字列処理（ワードカウント）やI/O・同期（チャネル）がボトルネックの場合、ループ制御構造の差は無視できる

2. **`flat_map`による遅延評価が効く場合** — 中間コレクションを生成しないイテレータチェーンは、ネストforループとほぼ同一コードにコンパイルされる

3. **データセットが十分に大きい場合** — `fold`のクロージャ呼び出しオーバーヘッドは定数的であり、データ操作コストの増加により相対的に小さくなる

### ゼロコスト抽象化が崩れる条件

1. **`Peekable`イテレータ** — `peek()`の内部キャッシュ（`Option`へのラップ/アンラップ）が各比較で発生し、単純なインデックスアクセスとの差が蓄積する

2. **`fold`によるアキュムレータのムーブ** — 所有権移動自体は低コストだが、クロージャ境界がコンパイラのループ最適化（ベクトル化、アンロール）を阻害する場合がある

3. **軽量なイテレーション本体** — 篩の「配列にfalseをセット」やマージの「2要素の比較とpush」のように1イテレーションのコストがナノ秒レベルの場合、ループ制御のオーバーヘッドが相対的に大きくなる

### 実務上の指針

- **パフォーマンスクリティカルでないコード**: 関数型スタイルを自由に使ってよい。可読性と保守性の向上が数%の性能差を上回る
- **ホットパスのタイトループ**: `Peekable` + `from_fn`パターンや、軽量操作での`fold`は避け、while/forループを使う
- **判断に迷う場合**: まず関数型スタイルで書き、プロファイラで検出されたら命令型に書き換える
